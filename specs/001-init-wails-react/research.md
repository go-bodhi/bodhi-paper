## 1. Project Scaffolding & Go Module

### Decision
Initialize the Wails v2 project using the official `react-ts` template with Go module path `github.com/go-bodhi/bodhi-paper`. The root files (`wails.json`, `main.go`, `app.go`, `go.mod`, `go.sum`, `build/`, `frontend/`) will be overlaid cleanly on the existing repository without disturbing `.git`, `.specify`, or `.agents`.

### Rationale
- Using the standard Wails CLI `react-ts` template creates the native desktop bridge and frontend bundler configuration with zero friction.
- The module path `github.com/go-bodhi/bodhi-paper` sets a clean, conventional Go package identity aligned with the project repository.

### Alternatives Considered
- Short module name `bodhi`: Rejected per user specification in favor of `github.com/go-bodhi/bodhi-paper`.

## 2. Backend `internal/` Layout: Minimal & Flat

### Decision
Keep the backend package layout inside `internal/` intentionally simple and flat:
- `internal/health.go`: Implements the baseline health and runtime status service.
- `internal/health_test.go`: Offline unit tests covering the health status service.

Do not introduce nested subdirectories (`internal/service/health/...`) at this stage; keep it flat until backend functionality expands.

### Rationale
- User explicit decision: "for now keep it simple, just health.go, for now we will just create a new file instead of structuring it in dir, later when backend will get larger then we will structure it".
- Avoids premature directory hierarchies and unnecessary boilerplate while still fulfilling the requirement for a private `internal/` backend package.
- Supports the Backend TDD gate: tests can run completely offline via `go test -v ./internal/...`.

### Alternatives Considered
- *Multi-layered directory hierarchy*: Deferred to future iterations when domain complexity warrants sub-packages.

## 3. Frontend Initialization: Unmodified Default Template

### Decision
Initialize the React + TypeScript frontend using the default `react-ts` Vite template generated by Wails. Do not build custom UI components, rich editors, or canvas views in this feature.

### Rationale
- User explicit decision: "don't build anything in frontend yet, just initialise the frontend".
- Constitution principles updated to focus strictly on local-first architecture and developer quality gates without unnecessary frontend assumptions upfront.
- Verifies that TypeScript compilation (`npm run build`) and hot module reloading (`wails dev`) operate cleanly out of the box before application-specific UI features are implemented.

### Alternatives Considered
- *Custom writing canvas UI*: Deferred to the dedicated editor feature.

---

## 4. Window Configuration & Runtime IPC Bridge

### Decision
- **Window**: Standard native window (1024x768 default width/height, resizable, native OS title bar and window controls).
- **IPC Bridge**: Standard Wails runtime struct binding via `app.go`, binding `GetHealth()` and `Greet()` to the frontend.

### Rationale
- Standard window provides native OS compatibility across Linux, macOS, and Windows without custom frameless drag-region handling.
- Wails automatically generates TypeScript bindings in `frontend/wailsjs/` allowing type-safe communication.
